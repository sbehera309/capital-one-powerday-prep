Technical Case 1

"Eeno" Real-Time Customer History Retrieval & Network Optimization

Recency:
Late 2025 – 2026 PowerDay Loops

Business Context

Capital One utilizes an intelligent conversational AI assistant named "Eeno" to address customer mobile app queries (e.g., "Why was my card declined?"). To evaluate context, the assistant queries an underlying event store for recent customer actions. You are presented with a legacy retrieval function, asked to evaluate its complexity, refactor it to accept dynamic windows, and optimize the distributed architecture.

Part A: Legacy Code Analysis & Evaluation

Legacy Python Function:

def retrieve_recent(self, customer_id, curr_time):
    result = []
    for i in range(5):
        val = self.store.retrieve(customer_id, curr_time - 5 + i + 1)
        if val is not None:
            result.append(val)
    return result
Q1: Complexity & Network

Time complexity is O(T) where T = 5. Makes 5 sequential point-lookup network round-trips returning records from curr_time - 4 to curr_time.

Q2: Dynamic Window

Refactor to accept dynamic window T (in minutes) starting from curr_time - time_window_minutes + 1.

Q3: Bottleneck at Scale

Iterating minute-by-minute introduces the Chatty API / N+1 Query anti-pattern. If T=60, service executes 60 sequential database roundtrips!

Part B: Optimized Production Implementation

Single Partition Range Query (O(1) Call)
Production Refactoring Code Redis / Cassandra 
class CustomerDataStore:
    def __init__(self, storage_client):
        self.store = storage_client

    def retrieve_recent(self, customer_id: int, curr_time: int, time_window_minutes: int) -> list:
        """
        Retrieves historical customer interactions within [curr_time - time_window_minutes + 1, curr_time].
        Replaces O(T) sequential network calls with a single partition range query.
        """
        if time_window_minutes <= 0:
            return []
        start_time = curr_time - time_window_minutes + 1
        return self.store.retrieve_range(
            partition_key=customer_id,
            start_timestamp=start_time,
            end_timestamp=curr_time
        )
package main

type StorageClient interface {
	RetrieveRange(customerID int64, startTimestamp, endTimestamp int64) ([]string, error)
}

type CustomerDataStore struct {
	store StorageClient
}

func NewCustomerDataStore(client StorageClient) *CustomerDataStore {
	return &CustomerDataStore{store: client}
}

func (cds *CustomerDataStore) RetrieveRecent(customerID int64, currTime int64, timeWindowMinutes int64) ([]string, error) {
	if timeWindowMinutes <= 0 {
		return []string{}, nil
	}
	startTime := currTime - timeWindowMinutes + 1
	return cds.store.RetrieveRange(customerID, startTime, currTime)
}
package com.capitalone.prep;

import java.util.Collections;
import java.util.List;

public class CustomerDataStore {

    public interface StorageClient {
        List<String> retrieveRange(long customerId, long startTimestamp, long endTimestamp);
    }

    private final StorageClient store;

    public CustomerDataStore(StorageClient storageClient) {
        this.store = storageClient;
    }

    public List<String> retrieveRecent(long customerId, long currTime, long timeWindowMinutes) {
        if (timeWindowMinutes <= 0) {
            return Collections.emptyList();
        }
        long startTime = currTime - timeWindowMinutes + 1;
        return store.retrieveRange(customerId, startTime, currTime);
    }
}

Part C: Logic Bug Identification & Resolution

Identified Bug: is_one_time == False forced the service to create a brand-new card on every single invocation, even when an existing multi-use virtual card should have been returned.
Resolved Logic Fix Code 
def generate_virtual_card(db, user_id: str, expiry_hours: int, is_one_time: bool) -> str:
    if is_one_time:
        return db.create_new_card(user_id, ttl_hours=expiry_hours)
    
    existing_card = db.find_active_reusable_card(user_id)
    if existing_card:
        return existing_card
    
    return db.create_new_card(user_id, ttl_hours=None)
package main

type CardDB interface {
	CreateNewCard(userID string, ttlHours *int) (string, error)
	FindActiveReusableCard(userID string) (string, error)
}

func GenerateVirtualCard(db CardDB, userID string, expiryHours int, isOneTime bool) (string, error) {
	if isOneTime {
		return db.CreateNewCard(userID, &expiryHours)
	}

	existingCard, err := db.FindActiveReusableCard(userID)
	if err == nil && existingCard != "" {
		return existingCard, nil
	}

	return db.CreateNewCard(userID, nil)
}
package com.capitalone.prep;

import java.util.Optional;

public class VirtualCardService {

    public interface CardDB {
        String createNewCard(String userId, Integer ttlHours);
        Optional<String> findActiveReusableCard(String userId);
    }

    private final CardDB db;

    public VirtualCardService(CardDB db) {
        this.db = db;
    }

    public String generateVirtualCard(String userId, int expiryHours, boolean isOneTime) {
        if (isOneTime) {
            return db.createNewCard(userId, expiryHours);
        }

        Optional<String> existingCard = db.findActiveReusableCard(userId);
        if (existingCard.isPresent()) {
            return existingCard.get();
        }

        return db.createNewCard(userId, null);
    }
}

System Design Question 2

Credit Limit Concurrent Throttler & Atomic Balance Reservation

"Design a system that tracks a customer's available credit in real time across multiple concurrent authorized users. If an account has a $1,000 credit limit and two transactions of $600 occur at the exact same millisecond, exactly one must approve and one must decline."

Redis Lua Distributed Atomicity Script

-- KEYS[1] = account:{account_id}:available_credit
-- ARGV[1] = transaction_amount
local available = tonumber(redis.call('GET', KEYS[1]))
local amount = tonumber(ARGV[1])
if available and available >= amount then
    redis.call('DECRBY', KEYS[1], amount)
    return 1 -- APPROVED
else
    return 0 -- DECLINED (INSUFFICIENT_CREDIT)
end

class CreditReservationService:

System Design Question 3

Distributed In-Memory Rate Limiter for Banking APIs

"Design a low-latency distributed rate limiter to protect customer-facing APIs from brute-force login attacks, scraping, and DDoS. Limit each API key or IP address to 100 requests per minute with <5ms latency overhead."

Redis Sorted Set (ZSET) Sliding Window Lua Script

local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local clearBefore = now - window

redis.call('ZREMRANGEBYSCORE', key, 0, clearBefore)
local currentRequests = redis.call('ZCARD', key)
if currentRequests < limit then
    redis.call('ZADD', key, now, now)
    redis.call('EXPIRE', key, math.ceil(window / 1000))
    return 1 -- HTTP 200 ALLOWED
else
    return 0 -- HTTP 429 RATE LIMITED
end
System Design Question 4

Real-Time POS Transaction Ingestion & Fraud Detection

"Design the authorization pipeline that ingests point-of-sale credit card swipe authorizations, evaluates limits and fraud heuristics, and returns an approval or decline in under 100ms. Scale: 10,000 writes/sec peak load."

Synchronous Fast Path (< 50ms SLA)

Queries Redis cluster to verify card state (Active vs Frozen), available credit, and 1-minute velocity. Returns HTTP 200 to POS terminal immediately.

Asynchronous Slow Path (Kafka + Flink)

Emits authorization events to Kafka topic partitioned by account_id. Apache Flink windowed job detects "Impossible Travel" anomalies (>600 mph velocity) and sets card to RESTRICTED.
