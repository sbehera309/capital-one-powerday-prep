Credit Card Account Management & Payment Portal

"Design a credit card account management application for a bank. The application must support customer credit card applications, viewing balance and real-time transaction activity, making monthly statement payments (minimum vs. custom balance), and generating daily, weekly, and monthly spending analytics."

1. API & Interface Specifications

POST /v1/payments
Header: Idempotency-Key: uuid
Body: {"account_id":"acc_99", "amount":150.00, "type":"STATEMENT_MIN"}
GET /v1/accounts/{id}/balance
Returns: {"current_balance":1240.50, "available_credit":8759.50}

2. Database Schema & Data Models

Aurora PostgreSQL (OLTP Ledger):
- payment_schedules (id PK, account_id FK, amount NUMERIC(12,2), status VARCHAR, created_at TIMESTAMPTZ)
- Index: (account_id, created_at DESC)
ClickHouse (OLAP Analytics):
- transaction_analytics (account_id, merchant_category, amount, txn_date Date) Engine = MergeTree PARTITION BY toYYYYMM(txn_date)

3. Failure Isolation & Resilience Strategy

  • • Zero Double-Debits: Redis SETNX payment:{key} "PROCESSING" EX 86400 blocks duplicate ACH submissions during network retries.
  • • CDC Decoupling: Debezium reads PostgreSQL Write-Ahead Logs (WAL) without locking transactional tables, streaming changes to Kafka.
  • • OLTP Protection: Heavy analytical queries (e.g., monthly spending category charts) run exclusively on ClickHouse columnar storage.

Credit Limit Concurrent Throttler & Atomic Balance Reservation

Reported Recency:

Exact Interview Prompt

"Design a system that tracks a customer's available credit in real time across multiple concurrent authorized users (e.g., primary cardholder and authorized users swiping cards simultaneously). If an account has a $1,000 credit limit and two transactions of $600 occur at the exact same millisecond, exactly one must approve and one must decline."

Click ▶ Run Concurrent Swipes to test 2 simultaneous $600 charges on a $1,000 credit limit.

1. Concurrency Model: Redis Lua vs Postgres Locks

• Postgres SELECT FOR UPDATE: Requires multi-millisecond disk/row locking overhead. Scalability degrades under high concurrent throughput.

• Redis Lua Scripting (Selected): Single-threaded Redis execution loop guarantees atomic check-and-decrement in sub-5ms without external locks.

2. Data Model & Cache Key Sharding

Redis Key: account:{account_id}:available_credit
Value: 100000 (Cents precision to prevent floating-point rounding errors)
System Design Question 3

Distributed In-Memory Rate Limiter for Banking APIs

Reported Recency:
Late 2024 – 2025 PowerDay Loops
Exact Interview Prompt

"Design a low-latency distributed rate limiter to protect customer-facing APIs from brute-force login attacks, automated scraping, and DDoS attempts. SLA Constraint: Overhead < 5ms; limit each API key or IP address to 100 requests per minute."

Interactive ZSET Sliding Window Simulator
Incoming Traffic API Gateway Req Key: client_ip
ZREMRANGEBYSCORE Purge Stale Timestamps Remove < (now - 60s)
ZCARD Count Check Active Requests < 100 ZADD Timestamp
Status Response HTTP 200 ALLOWED Over Limit -> HTTP 429
Click ▶ Send Requests to simulate sliding window counter evaluation.

1. Algorithm Choice: ZSET Sliding Window

• Fixed Window Flaw: Allows 2x spike across boundary (100 req at 0:59, 100 at 1:01 = 200 req in 2 seconds!).

• ZSET Solution: Stores timestamps as elements in a Redis Sorted Set. Purges elements older than 60s before calculating active count.

2. Cluster Sharding & Failover Policy

• Key hash slot partitioning: CRC16(api_key) % 16384.

• Fail-Open Policy for Banking APIs: If Redis cluster experiences regional outage, gateway fails OPEN to prevent locking out valid credit card users.

System Design Question 5

Peer-to-Peer Payment / Money Transfer Service (Zelle / Venmo)

Reported Recency:
2024 – 2025 PowerDay Loops
Interactive Double-Entry Saga Simulator
User A Send $100 to User B Idempotency Check
Postgres DB SELECT FOR UPDATE Lock Sender Row
Ledger Table Immutable Insert DEBIT -$100 / CREDIT +$100
Saga Orchestrator TX COMMIT Push Notification
Click ▶ Execute Transfer to test double-entry ledger bookkeeping.

1. Double-Entry Accounting Principles

Never mutate balance columns directly via UPDATE balance. Every money movement inserts paired immutable entries: DEBIT (sender) and CREDIT (recipient) in a single database transaction.

2. Distributed Transaction Saga Pattern

Saga Orchestrator manages multi-step transfers: Reserve Sender Funds $ o$ Validate Recipient $ o$ Ledger Commit $ o$ Notify. If recipient account is frozen, compensating transaction releases sender's hold.

1. Priority Queue & Consumer Isolation

Separate SQS FIFO queues for high-priority-fraud-alerts (dedicated worker pool) vs bulk-marketing-emails (rate-capped worker pool) to guarantee sub-3s delivery for security codes.

2. Exponential Backoff & DLQ Poison Pill Handling

Retries failed SMS dispatches with jittered exponential backoff ($2^n ext{s}$). After 3 failed attempts, poison pill events move to Dead Letter Queue (DLQ) for manual inspection and email channel fallback.

System Design Question 7

Distributed Banking Cache Architecture & Cache Stampede Defense

Reported Recency:
Early 2024 PowerDay Loops
Interactive Cache Stampede SETNX Lock Simulator
Redis Cache CACHE MISS Key Expired
SETNX Mutex Lock LOCK ACQUIRED Thread 1 Querying DB
Other Threads SPIN LOCK WAIT Zero DB Throttling
Cache Repopulated CACHE HIT (TTL 300s) Lock Released
Click ▶ Query Balance to simulate SETNX mutex lock cache stampede protection.

1. Cache Stampede (Thundering Herd) Solutions

• Mutex Lock (SETNX lock:key): Only 1 thread queries database on cache miss; other threads wait 50ms for cache repopulation.
• Jittered Expiration TTL: TTL = 300s + rand(0, 30s) prevents simultaneous key expiration spikes.

2. Cache Penetration Defense

Bloom Filter placed in front of cache filters out queries for non-existent account IDs before they ever touch Redis or PostgreSQL.

System Design Question 9 (New)

Active-Active Multi-Region Core Banking & Global Consistency

Reported Recency:
2025–2026 PowerDay Loops
Interactive Multi-Region Active-Active CRDT Simulator
AWS us-east-1 Primary Active Local Writes (20ms)
Cross-Region Sync Raft Consensus CRDT PN-Counter
Simulated Outage us-east-1 Offline Route 53 DNS Failover
AWS us-west-2 Zero Data Loss Sub-100ms Continuation
Click ▶ Simulate Regional Failover to test cross-region active-active resilience.

1. Active-Active Cross-Region Protocol

Deploy microservices across AWS us-east-1 and us-west-2. Reads and writes complete locally in <20ms. Asynchronous cross-region replication uses Conflict-Free Replicated Data Types (PN-Counter CRDTs) to reconcile ledger balances without cross-country lock waiting.

2. Regional Outage Failover (Zero RPO)

If AWS us-east-1 suffers complete outage, Route 53 latency DNS checks fail within 5 seconds and shift 100% of global traffic to us-west-2. Zero RPO (no lost committed transactions) via multi-region Raft quorum replication.

System Design & Architecture Cheat Sheet

Essential trade-offs, DB selection rules, serverless TCO comparison, and caching strategies for Capital One loops.

⚡ 1. AWS Serverless vs. Containerized (ECS Fargate / EC2)

Case 2 TCO Core
Serverless (AWS Lambda + DynamoDB)

✔ Pros: Zero idle costs, auto-scaling to zero, zero server maintenance, pay-per-execution.

✘ Cons: Cold start latency (degrades checkout conversion!), 15-min execution limit, higher unit cost at steady-state high throughput ($1,330/mo vs $1,016/mo at 4.3TB scale).

🎯 Best For: Bursty, event-driven, or asynchronous workflows (webhooks, notifications, low-traffic cron triggers).

Containerized (ECS Fargate + Aurora PG)

✔ Pros: Deterministic sub-50ms latency (NO cold starts!), lower cost for high steady-state volume (24% cheaper at 4.3TB scale), relational ACID compliance for account mappings.

✘ Cons: Baseline idle compute cost, container orchestration setup.

🎯 Best For: Core checkout payment APIs, virtual card tokenization, synchronous transaction processing.
