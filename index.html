Technical Case 1

"Eeno" Real-Time Customer History Retrieval & Network Optimization

Recency:
Late 2025 – 2026 PowerDay Loops

Business Context

Capital One utilizes an intelligent conversational AI assistant named "Eeno" to address customer mobile app queries (e.g., "Why was my card declined?"). To evaluate context, the assistant queries an underlying event store for recent customer actions. You are presented with a legacy retrieval function, asked to evaluate its complexity, refactor it to accept dynamic windows, and optimize the distributed architecture.

Part A: Legacy Code Analysis & Evaluation

Legacy Python Function:

def retrieve_recent(self, customer_id, curr_time):
    result = []
    for i in range(5):
        val = self.store.retrieve(customer_id, curr_time - 5 + i + 1)
        if val is not None:
            result.append(val)
    return result
Q1: Complexity & Network

Time complexity is O(T) where T = 5. Makes 5 sequential point-lookup network round-trips returning records from curr_time - 4 to curr_time.

Q2: Dynamic Window

Refactor to accept dynamic window T (in minutes) starting from curr_time - time_window_minutes + 1.

Q3: Bottleneck at Scale

Iterating minute-by-minute introduces the Chatty API / N+1 Query anti-pattern. If T=60, service executes 60 sequential database roundtrips!

Part B: Optimized Production Implementation

Single Partition Range Query (O(1) Call)
Production Refactoring Code Redis / Cassandra 
class CustomerDataStore:
    def __init__(self, storage_client):
        self.store = storage_client

    def retrieve_recent(self, customer_id: int, curr_time: int, time_window_minutes: int) -> list:
        """
        Retrieves historical customer interactions within [curr_time - time_window_minutes + 1, curr_time].
        Replaces O(T) sequential network calls with a single partition range query.
        """
        if time_window_minutes <= 0:
            return []
        start_time = curr_time - time_window_minutes + 1
        return self.store.retrieve_range(
            partition_key=customer_id,
            start_timestamp=start_time,
            end_timestamp=curr_time
        )
package main

type StorageClient interface {
	RetrieveRange(customerID int64, startTimestamp, endTimestamp int64) ([]string, error)
}

type CustomerDataStore struct {
	store StorageClient
}

func NewCustomerDataStore(client StorageClient) *CustomerDataStore {
	return &CustomerDataStore{store: client}
}

func (cds *CustomerDataStore) RetrieveRecent(customerID int64, currTime int64, timeWindowMinutes int64) ([]string, error) {
	if timeWindowMinutes <= 0 {
		return []string{}, nil
	}
	startTime := currTime - timeWindowMinutes + 1
	return cds.store.RetrieveRange(customerID, startTime, currTime)
}

System Design Question 1

Credit Card Account Management & Payment Portal

Reported Recency:
2025 – 2026 PowerDay Loops (Lead & Senior SWE)
Exact Interview Prompt

"Design a credit card account management application for a bank. The application must support customer credit card applications, viewing balance and real-time transaction activity, making monthly statement payments (minimum vs. custom balance), and generating daily, weekly, and monthly spending analytics."

SLA & Availability

Sub-second balance views with 99.99% availability.

Double-Debit Prevention

Zero double-debits on monthly payments during asynchronous ACH clearance (1–3 business days).

OLTP / OLAP Isolation

Spending analytics queries must not impact primary transactional database performance.

High-Level Data Flow Architecture 
[Client Mobile / Web] ──► [API Gateway (JWT Auth, SETNX Idempotency Check)]
                                │
                                ▼
                   [Card Account Microservice]
                   ┌────────────┼────────────┐
                   ▼            ▼            ▼
             [App Svc]    [Payment Svc]  [Analytics Svc]
                │               │              │
                ▼               ▼              ▼
          [Underwriting DB] [Ledger DB]  [ClickHouse OLAP]
                                │              ▲
                                └─► [Debezium CDC] ──► [Kafka] ──┘

Detailed Component Blueprint & Solutions

1. ACH Payment Asynchrony & Idempotency Engine

Payment submissions include an Idempotency-Key header validated in Redis via SETNX payment:{key} "PROCESSING" EX 86400. Since ACH transfers require 1–3 business days to settle over the NACHA network, payment records are inserted into Aurora PostgreSQL with status SCHEDULED_ACH. The customer's available credit line is conditionally updated immediately to provide instant feedback, while the ledger entry awaits final NACHA settlement.

2. Separating OLTP from OLAP via Change Data Capture (CDC)

To prevent heavy aggregation queries (SUM(...) GROUP BY category) from locking OLTP transactional databases, we use Debezium CDC. Debezium reads Aurora PostgreSQL Write-Ahead Logs (WAL) in real-time and streams row updates into a Kafka topic (account-transactions). Micro-batch sink connectors ingest these events into a columnar OLAP database (ClickHouse or Amazon Redshift), enabling sub-second spending analytics dashboards without touching the primary ledger DB.

System Design Question 2

Credit Limit Concurrent Throttler & Atomic Balance Reservation

Reported Recency:
2025 – 2026 PowerDay Loops
Exact Interview Prompt

"Design a system that tracks a customer's available credit in real time across multiple concurrent authorized users (e.g., primary cardholder and authorized users swiping cards simultaneously). If an account has a $1,000 credit limit and two transactions of $600 occur at the exact same millisecond, exactly one must approve and one must decline."

Architecture Solution: Redis Lua Distributed Atomicity

The Concurrency Problem: Reading balance in application memory → validating limit → writing back creates a race condition where both concurrent $600 transactions see $1,000 available credit and both approve ($1,200 total spend!).
The Solution: Maintain active available credit in an in-memory Redis cluster partitioned by account_id. Execute balance validation and decrement atomically inside an embedded Lua script. Because Redis executes Lua scripts on a single-threaded server loop, race conditions are mathematically impossible. 

-- KEYS[1] = account:{account_id}:available_credit
-- ARGV[1] = transaction_amount
local available = tonumber(redis.call('GET', KEYS[1]))
local amount = tonumber(ARGV[1])
if available and available >= amount then
    redis.call('DECRBY', KEYS[1], amount)
    return 1 -- APPROVED
else
    return 0 -- DECLINED (INSUFFICIENT_CREDIT)
end
Multi-Language Production Service Integration 
class CreditReservationService:
    def __init__(self, redis_client: redis.Redis):
        self.r = redis_client
        self._script = self.r.register_script(LUA_SCRIPT)

    def reserve_credit(self, account_id: str, amount: float) -> bool:
        key = f"account:{account_id}:available_credit"
        return self._script(keys=[key], args=[int(amount)]) == 1
func (s *CreditReservationService) ReserveCredit(ctx context.Context, accountID string, amount int64) (bool, error) {
	key := "account:" + accountID + ":available_credit"
	res, err := s.rdb.Eval(ctx, reserveLuaScript, []string{key}, amount).Result()
	return res.(int64) == 1, err

System Design Question 3

Distributed In-Memory Rate Limiter for Banking APIs

Reported Recency:
Late 2024 – 2025 PowerDay Loops
Exact Interview Prompt

"Design a low-latency distributed rate limiter to protect customer-facing APIs from brute-force login attacks, automated scraping, and DDoS attempts. SLA Constraint: Overhead < 5ms; limit each API key or IP address to 100 requests per minute."

Solution: Redis Sorted Set (ZSET) Sliding Window Counter

Why Fixed Window Fails: Fixed window rate limiters allow double the allowed request volume across window boundaries (e.g., 100 requests at 00:59 and 100 requests at 01:01).
ZSET Sliding Window: Uses timestamps as elements and scores in Redis Sorted Sets. Purges elements older than now - 60s before counting active requests. 

local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local clearBefore = now - window

redis.call('ZREMRANGEBYSCORE', key, 0, clearBefore)
local currentRequests = redis.call('ZCARD', key)
if currentRequests < limit then
    redis.call('ZADD', key, now, now)
    redis.call('EXPIRE', key, math.ceil(window / 1000))
    return 1 -- ALLOWED (HTTP 200)
else
    return 0 -- RATE LIMITED (HTTP 429)
end
System Design Question 4

Real-Time POS Transaction Ingestion & Fraud Detection

Reported Recency:
Mid 2024 – 2025 PowerDay Loops
Exact Interview Prompt & Constraints

"Design the authorization pipeline that ingests point-of-sale credit card swipe authorizations, evaluates limits and fraud heuristics, and returns an approval or decline in under 100ms. Scale: 10,000 writes/sec peak load; P99 latency < 80ms."

1. Synchronous Fast Path (< 50ms SLA)

Queries Redis Cluster to verify card status (Active vs Frozen), available credit, and 1-minute local frequency (INCR velocity:{card_id}:1min). If valid, decrements credit in Redis and immediately returns HTTP 200 APPROVED to the POS terminal.

2. Asynchronous Slow Path (Kafka + Flink)

Emits transaction events to Kafka topic txn-authorizations partitioned by account_id. Apache Flink windowed stream processing evaluates "Impossible Travel" anomalies over a 10-minute sliding window:
Velocity Speed = Distance(Loc2, Loc1) / (Time2 - Time1)
If speed > 600 mph, emits a high-priority security event and sets card state to RESTRICTED in Redis.

Peer-to-Peer Payment / Money Transfer Service (Zelle / Venmo)

"Design a real-time money transfer system where User A sends $100 to User B via email or phone number. Non-Functional Requirements: Strict ACID consistency on ledger updates, sub-second processing, and zero double-spending during network retries."

Double-Entry Append-Only Bookkeeping & Saga Pattern

Rule 1: Never mutate balance columns with UPDATE accounts SET balance = balance - 100.
Rule 2: Insert immutable paired DEBIT and CREDIT ledger rows inside a single database transaction: 

BEGIN TRANSACTION;
SELECT balance FROM accounts WHERE account_id = 'A' FOR UPDATE;
-- Verify balance >= 100

  (gen_random_uuid(), 'tx-123', 'B', 100.00, 'USD', 'CREDIT');
COMMIT;
System Design Question 6

Enterprise Multi-Channel Notification Engine

Reported Recency:
2024 PowerDay Loops
Exact Interview Prompt

"Design an event-driven system that triggers real-time alerts (SMS, Email, Push Notifications) for card transactions, account changes, and security events. Core Requirements: User notification preference filtering, priority queuing (fraud alerts within 2 seconds; marketing delayed), and isolation against third-party provider failures."

1. Priority Queuing & Dynamic Scaling

Allocate separate SQS queues partitioned by urgency: fraud-sms-queue (<2s SLA), transaction-push-queue, and marketing-email-queue. Worker pools scale independently via CloudWatch metrics.

2. Circuit Breakers & Dead-Letter Queues (DLQ)

Wrap external provider API invocations in circuit breakers. If Twilio/SendGrid returns HTTP 429 or 503, workers release messages with exponential backoff visibility timeout (2^retry × 5s). Route to sms-dlq after 3 failed attempts.

System Design Question 7

Distributed Banking Cache Architecture

Reported Recency:
Early 2024 PowerDay Loops
Exact Interview Prompt

"Design a distributed caching layer for mobile banking APIs serving customer balances and transaction summaries. Address cache stampedes, invalidation policies, and read-your-own-writes consistency."

Core Architecture Principles

  • 1. Caching Pattern: Cache-Aside with Write-Through Invalidation: On account mutation, write directly to primary DB, then immediately evict or update Redis key within the same transaction.
  • 2. Mitigating Cache Stampedes (Dog-Piling): Use Distributed Mutex Locking (SETNX lock:account:{id}). If a high-traffic cache key expires, only the first worker thread is permitted to query the database and rebuild cache; all other threads wait 50ms and retry reading cache.
  • 3. Read-Your-Own-Writes Consistency: Return monotonic mutation_version token in mutation headers. If an incoming read hits a replica with an older version, bypass cache and force a read from primary DB.
System Design Question 8

Smart Meter Telemetry Ingestion (Electric Utility Data)

Reported Recency:
2023 – Early 2024 PowerDay Loops
Exact Interview Prompt

"10 million smart meters transmit electricity usage metrics every 15 minutes. Design a scalable telemetry ingestion pipeline that supports customer dashboards and long-term analytics."

Math & Tiered Storage Blueprint

• Daily Writes = 10,000,000 × (24 × 60 / 15) = 10M × 96 = 960 Million events/day

• Ingestion Throughput = 960,000,000 / 86,400 ≈ 11,111 RPS

• Daily Data Volume (200 B payload) = 960M × 200 B ≈ 192 GB/day

Tiered Storage Architecture: Ingest via AWS IoT Core (MQTT) → Kinesis Data Streams → Hot Storage (0–30 Days): Time-Series DB (TimescaleDB / InfluxDB) partitioned by meter_id → Cold Storage (Historical Archival): Compress and store raw data in Amazon S3 (Apache Parquet format) queried on-demand via Amazon Athena.

⚡ 1. AWS Serverless vs. Containerized (ECS Fargate / EC2)

Case 2 TCO Core
Serverless (AWS Lambda + DynamoDB)

✔ Pros: Zero idle costs, auto-scaling to zero, zero server maintenance, pay-per-execution.

✘ Cons: Cold start latency (degrades checkout conversion!), 15-min execution limit, higher unit cost at steady-state high throughput ($1,330/mo vs $1,016/mo at 4.3TB scale).

🎯 Best For: Bursty, event-driven, or asynchronous workflows (webhooks, notifications, low-traffic cron triggers).

Containerized (ECS Fargate + Aurora PG)

✔ Pros: Deterministic sub-50ms latency (NO cold starts!), lower cost for high steady-state volume (24% cheaper at 4.3TB scale), relational ACID compliance for account mappings.

✘ Cons: Baseline idle compute cost, container orchestration setup.

🎯 Best For: Core checkout payment APIs, virtual card tokenization, synchronous transaction processing.
